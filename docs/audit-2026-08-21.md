# Audit critique du pipeline — 2026-08-21

**Portée :** intégralité du pipeline (`src/`, `dashboard/`, `data/prompts/`, `docs/`, CI, config).
**Méthode :** lecture exhaustive du code et des specs, exécution réelle des suites de tests/lint/type-check/couverture, vérification croisée avec des sources externes (documentation OWASP et OpenRouter, littérature LLM-as-a-judge, catalogue `/api/v1/models` en direct). Aucune affirmation chiffrée ci-dessous n'est une estimation — chaque nombre a été mesuré ou vérifié dans cette session.

---

## Résumé exécutif

Le pipeline est **structurellement solide** : architecture async cohérente, pré-évaluation déterministe qui économise réellement des appels API, jugement multi-LLM à l'aveugle dont les mitigations de biais sont directement alignées avec la littérature de référence, ledger de coût réel distinct de la projection TCO. Les tests passent (165/165), `ruff` et `mypy --strict` sont propres.

Mais trois angles morts concrets empêchaient de qualifier ce pipeline de « complet » :

1. **La documentation vivante n'a jamais fonctionné** — `mkdocs.yml` n'a jamais existé dans ce dépôt (aucun historique Git), `docs/reference/` était vide, `docs/documentation.md` (lié depuis le README) n'existait pas. `make docs-build` était cassé depuis toujours.
2. **La CI ne protégeait rien** — les étapes `ruff`/`mypy` se terminaient par `|| true`, donc un run rouge passait toujours au vert.
3. **Aucune protection contre un `TARGET_MODELS` invalide** — un identifiant de modèle `:free` périmé échoue silencieusement, noyé dans les erreurs de transport, sans jamais dire à l'utilisateur « ce modèle n'existe pas ».

Les trois ont été corrigés et vérifiés dans cette session (build `mkdocs --strict` désormais vert, CI Python fait réellement échouer un `ruff`/`mypy` en erreur, un garde-fou de validation de catalogue a été ajouté avec tests). Le reste de ce document détaille les constats, chiffre ce qui peut l'être, cite ses sources, et priorise ce qui reste à faire.

## 1. Ce qui est bien conçu et bien justifié (à ne pas casser)

| Choix | Justification vérifiée |
|---|---|
| SDK `openai` pointé sur OpenRouter (`base_url`) | Compatibilité native confirmée par la doc OpenRouter — évite de réimplémenter sérialisation/typage. |
| Pré-évaluation déterministe avant le juge LLM | Mesurable dans `results/` : sur un run réel (`benchmark_20260804_102607.csv` dérivé), **13 des 16 prompts qualité sont tranchés en pur code** (`quality_deterministic_prompt_count`), seuls 3 partent au juge — économie directe d'appels de jugement. |
| Panel de 3 juges Copilot à l'aveugle + alias + interdiction de favoriser la verbosité | Aligné avec Zheng et al., *Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena* (NeurIPS 2023, [arXiv:2306.05685](https://arxiv.org/abs/2306.05685)) : le papier documente précisément les biais de position, de verbosité et d'auto-préférence que ce design mitige, et montre qu'un juge de type GPT-4 atteint ~80 % d'accord avec des humains — donc l'approche est defendable, pas juste une intuition. |
| `actual_cost_credits` distinct du `tco_usd` projeté | La doc OpenRouter ([Usage Accounting](https://openrouter.ai/docs/use-cases/usage-accounting)) confirme que chaque réponse contient un champ `usage.cost` faisant autorité — la décision D11 de l'ADR est donc bien fondée, pas une supposition. |
| CER (`cer`) gelé si couverture < 80 % ou dimensions incomplètes | Évite une fausse précision statistique — bonne hygiène, cohérent avec le principe déjà appliqué ailleurs dans le code (`_MIN_QUALITY_COVERAGE_FOR_CER = 0.8`). |
| Ledger de coût réel exclut prompts/réponses (`CallCostRecord`) | Cohérent avec la contrainte SEC-001 déjà documentée ; vérifié en lisant le dataclass — aucun champ ne contient de texte libre. |
| 165 tests, `ruff check` et `mypy --strict` propres | Mesuré dans cette session (`pytest -q` → 165 passed ; `ruff check src/ tests/` → 0 violation ; `mypy src/ --strict` → 0 erreur sur 15 fichiers). |

## 2. Corrections appliquées dans cette session

Chaque correction ci-dessous a été vérifiée par exécution réelle (pas seulement relue).

### 2.1 Pipeline de documentation entièrement non fonctionnel → corrigé

**Constat :** `git log --oneline -- mkdocs.yml` ne retourne rien — ce fichier n'a **jamais existé**, dans aucun commit. `docs/reference/` était un dossier vide. `docs/documentation.md`, lié depuis le README (« *the documentation maintenance guide* »), n'existait pas. `make docs-build --strict` échouait donc à 100 % des tentatives, silencieusement, malgré l'affirmation du README selon laquelle « chaque pull request qui modifie les documents (...) lance une validation stricte ».

**Corrigé :**
- Création de `mkdocs.yml` (thème Material, `mkdocstrings` pour la référence API, `pymdownx.superfences` pour les diagrammes Mermaid déjà présents dans `workflow.md`/l'ADR, `admonition` pour les blocs `!!! tip/warning/info` déjà utilisés).
- Création de `docs/reference/api.md` avec des directives `::: module.path` pour tous les modules publics de `src/` et `dashboard/pareto.py` / `dashboard/security_viz.py`. `dashboard/app.py` est **volontairement exclu** — c'est un script Streamlit avec des effets de bord au chargement du module (import = exécution) ; l'inclure ferait planter le build.
- Création de `docs/documentation.md` (guide de maintenance, référencé par le README mais absent).
- Correction de 14 liens relatifs cassés dans `docs/brief-manager-2026-08-17.md` (pointant vers des fichiers hors de `docs/` — `../src/...py`, `../README.md`, `../.github/agents/...`) vers des URLs GitHub absolues, plus un ancre cassé vers une section de `workflow.md`.
- Ajout de `site/` à `.gitignore` (artefact de build, jamais suivi jusqu'ici).
- **Vérifié :** `mkdocs build --strict` termine maintenant avec `Documentation built in 5.56 seconds`, zéro avertissement.
- Ajout d'un job `docs` dans `.github/workflows/ci.yml` qui lance `mkdocs build --strict` sur chaque PR — jusqu'ici aucune CI ne validait la documentation.

### 2.2 CI qui ne protégeait rien → corrigé

**Constat :** dans `.github/workflows/ci.yml`, les étapes Python avaient :
```yaml
- name: Lint (ruff)
  run: ruff check . || true
- name: Type check (mypy)
  run: mypy src/ || true
```
Le `|| true` fait que **ces étapes ne peuvent jamais faire échouer la CI**, quel que soit le nombre d'erreurs. Seul `pytest` (sans `|| true`) faisait réellement échouer un run. Le README affirme pourtant « `ruff` propre » et « `mypy --strict` propre » comme garanties.

**Corrigé :** suppression des `|| true` sur les étapes `ruff`/`mypy`. Revérifié : `pytest` (165 passed), `ruff check` (0 violation), `mypy --strict` (0 erreur) sont tous verts après la correction — donc ce resserrement ne casse rien aujourd'hui, il empêche seulement une régression future de passer inaperçue.

*Non corrigé, volontairement* : le job `typescript` garde ses `|| true` (lint/type-check/test). Il n'y a **aucun fichier `.ts`/`.tsx` sous `src/`** aujourd'hui (les scripts npm eux-mêmes le détectent et no-opent), donc le risque réel est nul actuellement. Le resserrer maintenant introduirait un risque non vérifiable (le comportement par défaut de `vitest run` sans fichier de test n'a pas pu être testé dans cet environnement) pour un gain nul tant qu'aucun code TypeScript n'existe. **Recommandation :** resserrer ce job dès qu'un premier fichier `.ts` est ajouté au dépôt.

### 2.3 Aucune validation de `TARGET_MODELS` contre le catalogue réel → ajouté

**Constat (chiffré, voir §3.3) :** un identifiant de modèle `:free` périmé ou mal orthographié échoue sur **chaque** appel, mais cet échec est aujourd'hui indiscernable d'une simple instabilité réseau transitoire — il est absorbé dans `collection_errors` / `probe_error_count` et ne remonte qu'un message générique de dépassement de budget d'erreur, sans jamais dire *pourquoi*.

**Corrigé :** ajout de `_unknown_target_models()` dans `src/main.py`, appelée dans `CollectPipeline.run()` juste après la récupération du pricing live. Si un ou plusieurs modèles de `TARGET_MODELS` sont absents du catalogue retourné par `GET /models`, un message d'erreur explicite et actionnable est loggé (liste des IDs en cause + lien vers `openrouter.ai/models`), sans pour autant interrompre le run (les autres modèles valides du même run continuent d'être traités normalement). 3 tests unitaires ajoutés (`TestUnknownTargetModels`), tous verts.

### 2.4 Couverture de tests non mesurée → outillage ajouté

**Constat :** `pytest-cov` n'était pas dans les dépendances `[dev]`, donc la couverture n'était jamais mesurée en pratique. Une fois installée temporairement pour cet audit : **69 % de couverture globale**, avec `src/main.py` (le plus gros fichier, 517 lignes) à seulement **38 %** — voir détail au §3.1.

**Corrigé :** `pytest-cov>=5.0` ajouté aux dépendances `[dev]` de `pyproject.toml`, nouvelle cible `make test-cov` dans le Makefile. La mesure elle-même (améliorer la couverture de `main.py`) reste une recommandation (§3.1) — ce n'est pas un correctif ponctuel raisonnable à faire dans cette session sans discussion sur la stratégie de test (mock du client HTTP complet vs tests d'intégration).

### 2.5 Documentation obsolète / non sourcée → corrigée

- `docs/workflow.md` affirmait `make test # 147 tests` — le vrai nombre était 162 avant cette session (165 après les ajouts). Remplacé par une note pointant vers `make test-cov` plutôt que de re-figer un nombre qui re-deviendra faux au prochain commit.
- Ajout d'un encart sourcé sur les limites de débit OpenRouter des modèles `:free` dans `workflow.md` (détail complet au §3.3, chiffres tirés de la documentation officielle).
- L'ADR 0001 et `docs/index.md` citaient « OWASP LLM Top 10 (2025) » sans préciser que c'est désormais l'édition **archivée** ; ajout d'une note + lien vers l'édition 2026 en vigueur, et clarification que la pondération RSI est un choix interne non publié par OWASP (détail au §3.4).

## 3. Constats non corrigés — recommandations priorisées et chiffrées

### 3.1 Couverture de tests très inégale — `src/main.py` à 38 %

Mesuré avec `pytest-cov` :

| Fichier | Couverture | Instructions totales / manquées |
|---|---|---|
| `src/main.py` | **38 %** | 517 / 320 manquées |
| `src/api/fake_client.py` | 40 % | 96 / 58 manquées |
| `src/observability/tracker.py` | 88 % | — |
| `src/api/openrouter_client.py` | 81 % | — |
| `src/evaluators/quality_judge.py` | 87 % | — |
| `src/evaluators/cost_analyzer.py` | 90 % | — |
| `src/evaluators/security_scanner.py` / `quality_metrics.py` / `deterministic_eval.py` | 97-98 % | — |
| **Total** | **69 %** | 1494 / 461 manquées |

`src/main.py` est à la fois le plus gros fichier du dépôt (517 lignes, 13,6 % du total `src/` de 3799 lignes) et le moins couvert. En pratique, les tests existants (`test_main.py`, 9 classes de tests) couvrent bien les fonctions **pures** (`_rebuild_quality_df`, `_enforce_collect_error_budget`, et maintenant `_unknown_target_models`), mais **aucun test n'exerce `CollectPipeline.run()`, `MergePipeline.run()`, `AsyncPipeline.run()`, `DryRunPipeline.run()` ou `main()` de bout en bout** — l'orchestration async elle-même n'est validée qu'à la main via `make dry-run`.

**Recommandation :** ajouter des tests d'intégration légers pour `CollectPipeline.run()` avec un `AsyncOpenRouterClient` entièrement mocké (`unittest.mock.AsyncMock`), sur le modèle de ce qui existe déjà pour `FakeAsyncOpenRouterClient` en dry-run. Prioriser `main()` (dispatch CLI, actuellement 0 % testé) et `CollectPipeline.run()` (le chemin qui dépense du budget API réel).

### 3.2 OWASP LLM Top 10 : édition citée obsolète, pondération RSI non sourcée

Vérifié en direct sur [owasp.org/www-project-top-10-for-large-language-model-applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/) : cette page se présente elle-même comme un **« legacy entry point »** archivé. La version courante, selon OWASP lui-même, est l'**[OWASP GenAI LLM Top 10 2026](https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/)**, publiée le 4 août 2026. Le dépôt (README, ADR 0001, `docs/index.md`, `security_scanner.py`, `data/prompts/owasp_probes.json`) référence uniquement l'édition 2025 — désormais une version en retard par rapport à la source de vérité que le projet cite lui-même.

Par ailleurs, **OWASP ne publie aucune pondération numérique officielle par catégorie**. Les poids RSI du dépôt (`LLM01=0.25, LLM02=0.20, LLM06=0.15, LLM07=0.15, autres=0.02-0.05`) sont un choix interne, cohérent et documenté dans l'ADR, mais présenté avec une formulation (« *reconnu par criticité enterprise* ») qui pourrait laisser croire à une légitimité externe qu'il n'a pas. Ce n'est pas un défaut de conception — c'est un jugement d'expert raisonnable — mais l'attribution doit être explicite.

**Recommandation (non faite dans cette session — ampleur trop grande pour un correctif ponctuel fiable) :** planifier une révision de `data/prompts/owasp_probes.json` et de `_RSI_WEIGHTS` face à la structure de catégories de l'édition 2026, et relabelliser la pondération RSI comme un choix interne assumé plutôt que comme une pondération « reconnue ».

### 3.3 Limites de débit OpenRouter : un run par défaut sur modèles `:free` peut dépasser le plafond gratuit

Vérifié en direct sur la [documentation officielle des limites OpenRouter](https://openrouter.ai/docs/api-reference/limits) — le plafond est **par compte**, pas par clé API (« *Making additional accounts or API keys will not affect your rate limits* ») :

| Crédits achetés (cumul, historique) | Requêtes/minute | Requêtes/jour |
|---|---|---|
| < 10 USD | 20 | 50 |
| ≥ 10 USD | 20 | 1000 |

Calcul pour un `make collect` par défaut (3 modèles `:free`, `QUALITY_REPETITIONS=1`) :

- Qualité : 16 prompts × 3 modèles = **48 requêtes**
- Sécurité (5 sondes intégrées) : 5 × 3 = **15 requêtes**
- **Total run standard : 63 requêtes — déjà 26 % au-dessus du plafond de 50/jour** d'un compte sans crédit.
- Avec `SECURITY_PROBES_PATH=data/prompts/owasp_probes.json` (30 sondes) : 48 + (30 × 3) = **138 requêtes — 2,76× le plafond**.

Ce risque n'était documenté nulle part avant cette session (il est corroboré indépendamment par le calcul de coût déjà présent dans `docs/brief-manager-2026-08-17.md`, qui utilise exactement les mêmes 63/138 requêtes pour justifier un budget — bon signe de cohérence interne, mais personne n'avait relié ce chiffre au plafond de rate-limit officiel). Ajouté à `docs/workflow.md` dans cette session (voir §2.5).

**Recommandation additionnelle (non implémentée) :** un garde-fou runtime dans `CollectPipeline` qui estime le nombre de requêtes prévues avant de lancer `asyncio.gather` et avertit si ce nombre dépasse un seuil sûr pour un compte sans crédit — actuellement l'utilisateur ne le découvre qu'après coup, via des `429`.

### 3.4 Identifiants de modèles par défaut potentiellement obsolètes

Le catalogue live `GET /api/v1/models` (419 modèles, récupéré dans cette session) confirme que les identifiants suivants **existent bien** et correspondent aux données déjà présentes dans `results/benchmark_20260804_102607.csv` (mêmes `context_length`, bon signe que ce run historique est authentique) :

- `google/gemma-4-31b-it:free`, `nvidia/nemotron-3-super-120b-a12b:free`, `nvidia/nemotron-3-ultra-550b-a55b:free`, `cohere/north-mini-code:free`, `poolside/laguna-s-2.1:free`, `openai/gpt-oss-20b:free`

En revanche, **deux identifiants n'ont pas été retrouvés** dans le catalogue récupéré :

- `meta-llama/llama-3.3-70b-instruct:free` (valeur par défaut de `Settings.target_models` dans `src/core/config.py`) — seule la variante payante `meta-llama/llama-3.3-70b-instruct` (sans suffixe `:free`) a été trouvée.
- `qwen/qwen3-coder:free` (exemple dans `.env.example`) — seules des variantes payantes (`qwen3-coder-flash`, `-plus`, `-next`) ont été trouvées.

*(Réserve méthodologique : la réponse JSON de 419 modèles a été résumée par l'outil de récupération web ; une omission de l'outil n'est pas totalement exclue. D'où l'intérêt du garde-fou ajouté au §2.3, qui vérifie ce point à chaque run réel plutôt que de se fier à une vérification ponctuelle.)*

**Recommandation :** revérifier ces deux identifiants avant le prochain run payant ; le garde-fou du §2.3 les signalera désormais explicitement s'ils sont toujours invalides.

### 3.5 Suite qualité : petite, single-shot par défaut

16 prompts pour 6 dimensions (moyenne 2,7 prompts/dimension), et `QUALITY_REPETITIONS=1` par défaut — `quality_stability_score` reste donc `null` tant que cette variable n'est pas relevée à ≥ 2. C'est un choix assumé et documenté (« *large screen* », pas un remplacement de `gen-e2-eval »), mais il mérite d'être rappelé explicitement : le score qualité d'un run par défaut n'a **aucune mesure de stabilité inter-répétitions**. **Recommandation :** imposer `QUALITY_REPETITIONS≥2` pour tout résultat utilisé en aide à la décision de shortlist (déjà suggéré dans le README, mais pas techniquement forcé).

### 3.6 Déploiement GitHub Pages : documenté, jamais implémenté

Le README affirme : « *A push to main publishes the resulting site to GitHub Pages* ». Aucun workflow de déploiement n'existe dans `.github/workflows/`. Le job `docs` ajouté dans cette session (§2.1) valide la construction stricte sur chaque PR, mais **ne publie rien**. **Recommandation :** ajouter un job de déploiement (`actions/deploy-pages@v4` + permissions `pages: write` / `id-token: write`) déclenché sur push vers `main`, une fois GitHub Pages activé dans les paramètres du dépôt (prérequis déjà correctement documenté dans le README).
